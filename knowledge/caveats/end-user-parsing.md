This is the most consequential data-quality problem in the project. Every
session-level number produced by [[project/llmoxie-analysis]] is conditional on
it.

## The mechanism

LiteLLM has no notion of a "session". The gateway learns about device, account,
and session only because the client packs all three into the free-form
`end_user` field. `_parse_end_user` in [[upstream/reader-flattening]] tries to
unpack it:

1. `json.loads` — the well-behaved case.
2. Failing that, `json.loads` again with `\"` un-escaped to `"`, for records
   exported through PostgreSQL's `row_to_json()` (added in upstream `3e9a694`).
3. Failing that, a regex:
   ```python
   r"user_(?P<device_id>[0-9a-f]*)_account_(?P<account_uuid>.*?)_session_(?P<session_id>[0-9a-f-]+)"
   ```
4. Failing all three, return
   `{"device_id": "", "account_uuid": "", "session_id": ""}` — silently. The
   warning this step used to log was removed in `3e9a694`.

There is no negotiated contract here. The format is whatever the client happened
to send, and different clients — and different versions of the same client —
send different things.

## The magnitude

!!! danger "About 25% of Jan–Mar 2026 requests have no usable session_id"

    Those requests are not merely mislabeled. They are **dropped** from session
    grouping entirely: `build_sessions` filters on `session_id == ""` and
    counts them out.

Two consequences follow immediately.

**Session counts are a lower bound, and a biased one.** If parse failure
correlates with a particular client or client version — which is likely, since
the format is client-determined — then the surviving sessions over-represent
whichever clients happened to format `end_user` correctly. A statement like
"most sessions use model X" may be a statement about one client's users.

**Request-level and session-level totals will not reconcile.** Summing spend
across sessions gives a smaller number than summing spend across requests. That
gap is the dropped quarter, not an arithmetic error.

## Upstream now hides the gap instead of closing it

Everything above describes upstream at `ec5d8b2`, which is also what the ~25%
figure was measured against. Commit `3e9a694` (PR #167, 2026-09-18) changes what
happens to an unparsed request. `_base_row` and the new streaming path in
[[upstream/session-reconstruction]] both compute:

```python
session_id = eu["session_id"] or record.get("session_id")
```

So a request whose `end_user` cannot be parsed is no longer dropped. It is
grouped under LiteLLM's native `session_id` instead.

!!! danger "The native session_id is one value per request"

    [[datasets/jan-mar-2026-findings]] counted **13,221 distinct values across
    13,291 records** in that column, and upstream's own test comment calls it
    _"a per-request UUID generated by LiteLLM, not the Claude Code session"_.
    Falling back to it does not recover the conversation. It turns each
    unparsed request into its own one-request "session".

What follows is **inferred** from the code and the profiled counts; nobody has
re-run the grouping at `3e9a694` yet. Re-running `group_sessions` on the
Jan–Mar 2026 extract and comparing the session count with the 279 measured
before would confirm it.

- **Session counts stop being a lower bound and become inflated.** The roughly
  one quarter of requests that used to be dropped should reappear as thousands
  of singleton sessions, swamping the real ones. Any per-session average —
  requests per session, spend per session, session length — is pulled toward
  the singleton.
- **`skipped_session_count` stops measuring parse failure.** It now counts only
  records where both `end_user` and the native column are empty. The native
  column is populated on every record in the extract, so the count should read
  near zero while the underlying problem is unchanged.
- **Nothing in the logs says so**, because the parse-failure warning was removed
  in the same commit.
- Request-level and session-level spend totals should now reconcile, which
  removes the one symptom that used to reveal the gap.

A pipeline built on `3e9a694` therefore has to tell the two kinds of session
apart itself: record whether each `session_id` came from `end_user` or from the
fallback, and report the fallback share next to every session count.

## What the pipeline must do about it

Issue #1 makes this a hard requirement: **every pipeline run must log
`skipped_session_count`**. The prototype already computes it as the second
element of `build_sessions`'s return tuple (see
[[upstream/session-reconstruction]]); the production run statistics must surface
it rather than discard it.

The figure belongs in `PipelineRunStats` and in any report built on the output.
A session count published without its companion skip count is incomplete.

At upstream `3e9a694` the second element of that tuple no longer carries this
meaning, for the reason given above. The requirement is about `end_user` parse
failures, so the production count has to be taken on the parsed `end_user`
result, before any fallback to the native column.

## An era-specific measurement

The "~25%" figure was measured on the January–March 2026 dump. Per
[[platform/llmoxie-timeline]], that dump necessarily came from the LiteLLM
spend-log path, because [[platform/adls-logger]] did not exist until 2026-05-08.
So the figure characterizes **LiteLLM-sourced data from early 2026** — not the
ADLS path, and not the present day.

Do not assume it generalizes in either direction. Client behavior changes over
time, and the rate should be recomputed per source and per period rather than
carried forward as a constant. Because every row carries `data_source` (see
[[pipeline/analytics-schema]]), that recomputation is a group-by away.
